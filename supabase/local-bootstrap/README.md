# Experimental fresh local bootstrap

Local testing only; this is not a production migration, a replacement for a Supabase environment, or evidence of production schema parity. Requires a fresh disposable database with Supabase-compatible auth schema, roles and realtime publication already present. Never use against a populated or remote database. Set LOCAL_CONTAINER to a disposable container named `job-priv2-*` and LOCAL_DATABASE to its fresh database named `job_priv2_*` and run `supabase/local-bootstrap/run.sh` from the repository root. It stops on the first SQL failure and executes each file in its own transaction.

`migration.sql` provides the household baseline; `phase3-compat.sql` adds the missing 001 tables and columns without overwriting its profile policies; neither this path nor its Auth stub establishes a working signup trigger. Migration 002 and 003–009 follow. The 010 local copy substitutes owner membership for an absent `households.created_by` and refuses any pre-existing household; it is only valid for a fresh database. Then 011–025 and the timestamped migration run. `final-compat.sql` removes a self-referential policy left by the baseline that otherwise makes household-member and shopping queries error; migration 019's helper-based policy remains. Historical files remain unchanged. If these copies or the file list drift, reconcile deliberately; this is not an automatically maintained schema snapshot.

Auth and Realtime stubs prove SQL compatibility and RLS only. Actual managed Auth, storage, application login, UI, integrations, missing historical schema and live privileges need independent verification. In particular, no conclusion about production policy state follows from this reconstruction.
